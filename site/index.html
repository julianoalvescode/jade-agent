What Jade can take on

From a one-line bug to a feature that spans the API and the UI. She asks only when a choice changes the contract, the data or the security.

Ticket to pull request

Reads the Jira ticket and linked Confluence pages, checks the back-end contract, builds it and opens the PR with evidence.

“Implement PROJ-123 and prepare the PR.”

Figma to code

Reads one node, maps it to the components you already have and keeps the 8-point grid. No screen recreated from memory.

“Build this frame with our design system.”

Full-stack features

Designs the endpoint and the screen together: pagination, authorization per resource, indexes and matching types on both sides.

“Add an orders list with filters, API and UI.”

Reviews and audits

Reviews a diff for correctness, OWASP risks, performance and accessibility, with findings by file and line.

“Review this PR for security and performance.”

Five pillars on every change

Checked in proportion to risk. When they conflict, the order is security, correctness, accessibility, performance, then taste.

Agree first, then build

Every Jade run happens inside OpenSpec. Questions stay in explore. Any code change, even a small fix, gets a change, and a task is ticked only when its evidence exists.

  1. 01

    Explore

    Reads the repo and weighs options on the five pillars. No code.

  2. 02

    Propose

    Proposal, delta specs, design with one line per pillar, and tasks.

  3. 03

    Apply

    Builds task by task with the right skills for front end, back end, Figma and contract.

  4. 04

    Verify

    Runs the quality gate against every requirement and scenario.

  5. 05

    Archive

    Only when the gate says READY and you agree. Specs keep what shipped.

No proof, no “done”

Every task ends with a matrix: criterion, implementation, evidence and state. Written, validated, PR open, merged and deployed are never mixed up.

  • PASS Checked, with concrete evidence.
  • FAIL Checked, and the requirement broke.
  • BLOCKED Access, data or a decision is missing.
  • NOT RUN Relevant but not run. Reason and risk stated.
  • N/A The change does not touch it.

Set up in four steps

Needs Python 3.10+ and Git. Node is only needed for the OpenSpec CLI.

  1. Install Jade into your project

    git clone https://github.com/julianoalvescode/jade-agent.git
bash jade-agent/scripts/install-skills.sh claude-code --project /path/to/project

    Add --core-only for the eight Jade skills without network, or --replace to update with a backup in .jade/backups/.

  2. Set up OpenSpec

    npm install -g @fission-ai/openspec@latest
cd /path/to/project && openspec init

  3. Connect your tools

    claude mcp add --transport http atlassian https://mcp.atlassian.com/v2/mcp
claude mcp add --transport http figma https://mcp.figma.com/mcp

    Finish OAuth in /mcp. Copy jade.project.example.json to jade.project.json and fill in only what you know.

  4. Ask Jade

    Use the Jade agent to implement ticket PROJ-123. Read the linked documents, check the back-end contract and validate the criteria. Prepare the PR with the evidence.

Questions

Is Jade safe to run on my repo?

She does not open .env or print secrets. She asks before writing to Jira, Confluence or GitHub, never force pushes and never skips required checks. Infrastructure, permissions and deploys need an explicit request.

Does Jade change my back end?

Only when the back end is part of the request. Otherwise she checks the contract and records the dependency.

What if the OpenSpec CLI is not installed?

Jade asks you once to install it. Meanwhile she writes the change files by hand in the same structure and marks openspec validate as NOT RUN.

Will it overwrite my CLAUDE.md, AGENTS.md or .mcp.json?

No. The installer reports conflicts before writing. With --replace it keeps a backup of every file it changes.

What happens without Figma access?

The visual step is marked BLOCKED. Jade does not recreate a screen from memory. Work that does not depend on the design can continue.

Are the community skills trusted?

Each one is pinned to an exact commit and checked by name. The installer never runs third-party scripts. Pinning gives traceability; it is not a security audit.
